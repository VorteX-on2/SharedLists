# Use a single cursor-driven synchronization stream

Each foreground client synchronizes through one challenge-authenticated bidirectional `Sync` RPC with a strict opening, syncing, and live state machine. The client opens with a synchronization cursor containing a persistent server generation and last applied revision; the server then sends bounded, transactionally consistent snapshot chunks when the cursor is unusable or contiguous journal batches when it can resume, with one durably acknowledged batch and at most one submitted operation in flight.

Snapshots are staged and atomically replace canonical cached state, which remains read-only until reconnect catch-up completes. Editing is available only in the live state: the client durably retains its single unconfirmed operation until the matching journal entry arrives, and after an ambiguous disconnect, catch-up either reconciles that entry or the client resubmits the same operation ID. Every first-seen well-formed operation receives one durable journal revision regardless of whether it is applied, ignored, or rejected; each journal entry carries the canonical payload, outcome, and authoritative state effects and serves as the normal acknowledgement to its sender.

The protobuf schema evolves through backward-compatible field additions without protocol-version negotiation. Domain rejection and terminal-deletion outcomes do not end synchronization, while authentication and sequencing violations, mismatched operation-ID reuse, corrupted state, supersession, storage failure, and slow-consumer overflow terminate the stream; clients resume from their last atomically persisted cursor. The protocol has no application heartbeat or close handshake: HTTP/2/TCP keepalive detects dead connections, and a foreground client cancels the stream immediately when backgrounded.
